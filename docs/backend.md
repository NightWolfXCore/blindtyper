# Бэкенд: устройство, интеграция и запуск

## Слои

- `public/index.php` — точка входа и маршруты будущих HTML-страниц.
- `Http/Request` — чтение и проверка JSON, лимит тела, query-параметры.
- `Http/Session` — серверная cookie-сессия, ротация ID и CSRF.
- `Controller/ApiController` — маршрутизация API и проверка доступа; формат ответа задаёт `Http/Application`.
- `Service/AuthService` — регистрация, проверка пароля, представление владельца аккаунта.
- `Service/TrainingService` — жизненный цикл тренировки, транзакции, координация начисления.
- `Domain/Rules`, `Domain/Scoring` — чистые правила, не зависящие от HTTP/MySQL.
- `Repository/*` — только SQL и преобразование результатов чтения.
- `Support/Clock` — часы: настоящие в приложении, управляемые в тестах.

Новые методы API добавляются в контроллер, бизнес-правила — в сервис/Domain, запросы — в Repository. Содержимое cookie и присланные клиентом итоги не являются источником XP.

## Для разработчика фронтенда

API: `/api/v1`, тот же домен, JSON UTF-8. Схемы и поля находятся в [контракте](api-contract.md). При создании POST передавайте объект, в том числе `{}` для start/logout.

```js
let csrfToken;

async function refreshCsrf() {
  const response = await fetch('/api/v1/auth/csrf', { credentials: 'same-origin' });
  const body = await response.json();
  if (!response.ok) throw body.error;
  csrfToken = body.data.csrf_token;
}

async function api(path, { method = 'GET', data } = {}) {
  const headers = { Accept: 'application/json' };
  if (method === 'POST') {
    if (!csrfToken) await refreshCsrf();
    headers['Content-Type'] = 'application/json';
    headers['X-CSRF-Token'] = csrfToken;
  }
  const response = await fetch(`/api/v1${path}`, {
    method,
    credentials: 'same-origin',
    headers,
    ...(method === 'POST' ? { body: JSON.stringify(data ?? {}) } : {}),
  });
  const body = await response.json();
  if (!response.ok) throw { status: response.status, ...body.error };
  if (['/auth/login', '/auth/register', '/auth/logout'].includes(path)) {
    csrfToken = undefined; // сервер ротирует токен; запросить заново перед следующим POST
  }
  return body.data;
}
```

Этот фрагмент — пример для реализации `public/assets/js/api.js` участником фронтенда. Страницы — `public/pages/index.html`, `login.html`, `register.html`, `profile.html`, `leaderboard.html`; URL маршрутов перечислены в архитектуре. Ресурсы хранить в `public/assets/`. PHP подключает только фиксированный набор HTML-файлов; произвольные имена файлов из URL не исполняются.

Порядок тренировки: catalog → POST sessions → POST start → таймер и ввод → POST finish. `performance.now()` отсчитывается после успешного start. Для каждой попытки один event с seq=1,2,3…; ошибочный ввод сохраняется в журнале и не продвигает позицию. Не храните журнал на сервере по одному нажатию. После сетевой ошибки finish повторяйте **тот же массив**, а не создавайте новую тренировку. После успешного finish используйте серверный result/progress.

При 401 предложите войти; при CSRF_INVALID обновите токен и предложите повторить действие. Не повторяйте автоматически все POST: повтор создания тренировки бросает предыдущую. При неопределённом исходе start создайте новую тренировку с новым таймером.

## Для разработчика БД

Запросы написаны по [контракту БД](database-contract.md). В `tests/fixtures/schema.sql` есть выполняемый пример совместимой схемы, в `tests/fixtures/seed.php` — идемпотентное наполнение для разработки. Это не производственные миграции. PHP проверяет NFC, LF, длину текста и корректность входных настроек; правило сложности задаётся содержимым упражнения.

Поле `session_character_stats.expected_char` в примере имеет MySQL 8 collation `utf8mb4_0900_bin` (NO PAD): пробел, регистр и `е/ё` должны различаться. Не заменяйте его на сравнение, игнорирующее пробелы. Первичный ключ — session_id + expected_char. Хэши/UUID сравниваются побайтно.

Создание, старт и finish сначала блокируют users, затем training_sessions. Соблюдайте этот порядок при расширении приложения. В finish профиль, статистика символов, достижения и результат меняются в одной транзакции. finish_response сохраняется для повторного ответа; порядок ключей JSON MySQL может изменить, значения остаются прежними.

При передаче производственной схемы замените команду dev-database на установщик миграций разработчика БД, а затем прогоните integration-тесты на отдельной базе. В API EXERCISE_UNAVAILABLE (503) означает отсутствие подходящего активного упражнения; код не подменяет содержание фиктивным результатом.

## Ограничения частоты и эксплуатация

Лимиты: 20 запросов register/login на IP за 15 минут; 10 на email за 15 минут; 5 регистраций на IP в час; 10 созданий тренировки на пользователя в минуту. Они учитывают попытки, включая успешные. Новая cookie не сбрасывает лимит. IP берётся только из REMOTE_ADDR; X-Forwarded-For не считается доверенным без отдельной настройки прокси.

Лимитер использует файлы с flock в `storage/rate-limits`. Он подходит для одного сервера с несколькими PHP-процессами. Несколько серверов требуют общего хранилища лимитов, например Redis. Старые файлы лимитера можно удалить при остановленном приложении; активные файлы во время работы не удалять. PHP-сессии находятся в `storage/sessions`; время неактивности ограничено серверным сроком 24 часа (штатная сборка мусора PHP). При необходимости настройте внешнюю очистку файлов сессий согласно настройкам PHP. Тестовые процессы используют отдельный `storage/test`.

Для публикации используйте Nginx/Apache + PHP-FPM, document root `public`, APP_ENV=production и HTTPS APP_URL. Настройте перенаправление на HTTPS на веб-сервере. Cookie Secure определяется APP_URL. DB-пользователю приложения нужны права чтения/записи; DDL выполняется отдельной учётной записью установщика миграций. Каталог storage должен быть доступен на запись PHP и закрыт от HTTP.

Пример Nginx-конфигурации находится в `docker/nginx.example.conf`; PHP CLI server и Compose предназначены для локальной разработки. Секреты передаются через окружение. Настройте на веб-сервере лимит тела не меньше 2 МБ; приложение ограничивает JSON 2097152 байт и возвращает JSON-ошибку. Ограничение тела самим прокси может вернуть собственную страницу 413 — фронтенд должен обрабатывать и такой ответ.

В журнал ошибок не записываются пароли, cookie, тело запросов, SQL-параметры и сообщения исключений с возможными секретами. Ответ 500 содержит request_id, по которому можно найти тип исключения и строку кода в серверном журнале.

## Демонстрационный аккаунт

Необязательная команда только для development/test:

```sh
# DEMO_PASSWORD передайте через окружение; не сохраняйте его в Git или истории команд.
docker compose exec -e DEMO_PASSWORD -e DEMO_EMAIL app php bin/create-demo.php
```

Email по умолчанию demo@example.org, начальный XP=900 (уровень 4), is_demo=true. Если email уже занят, скрипт остановится без изменения аккаунта. Демо-пользователь исключён из рейтинга.

## Установка в облаке с HTTPS-прокси

В этой среде Docker build потребовал передачи существующих proxy build args и разрешения имени прокси через `--add-host`; Composer — подключения уже доверенного системного CA через COMPOSER_CAFILE. Это настройка конкретного окружения: адреса и сертификаты не включаются в репозиторий. Не отключайте TLS или проверку подписей пакетов.

Lock-файл использует официальный codeload.github.com вместо api.github.com для архивов GitHub, поскольку API-домен здесь возвращал 403. Версии и точные Git commit refs зафиксированы; зависимости устанавливаются обычным composer install.
